# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Opus never writes code

If the running model is Opus, it may only brainstorm and plan. It must never write or edit code itself. Any coding task is delegated to a subagent running on a weaker model (the Agent tool's `model: "sonnet" | "haiku"`).

**Spec → code, no plan by default.** A feature gets a written spec (decisions, contract, files to touch, tests) and goes straight to the subagent, which writes its own tests and code from it. Write an implementation plan only when the work is split across several subagents, and then as a short task list (task, files, dependencies) — **never code in a plan**: a plan with full code is the implementation written twice, in Opus tokens. This overrides the superpowers `brainstorming` → `writing-plans` handoff.

## Code quality

Code must be clean. No god-files: one file, one responsibility. A file that mixes several sections, components or concerns must be split before it grows (rule of thumb: around 150 lines or more than one exported component per concern is the signal), and `routes/` files stay thin. Do not leave dead code, unused exports or commented-out code behind.

## What this is

FoodFen's web client (Vite + React 19 + TypeScript SPA): the **restaurant owner portal and the admin area**. The nutrition tracker itself lives in the mobile app.

**Scope is fixed.** End users get only the landing page, sign-in/register/password flows, and a basic personal-info page (`/app`). Do not build tracker features on the web (food logging, AI analysis, goals, water/weight/activity logs, streaks, quests, quizzes, coins, chat, Premium checkout) even though the BE exposes them, and do not invent new end-user screens. Anything beyond this scope needs an explicit request.

Siblings in the parent folder: `../FoodFenBE` (FastAPI) and `../FoodFenFE` (Expo mobile app). The mobile app's libraries and `CLAUDE.md` rules do not apply here; read them for product context only. All UI copy is Vietnamese.

## Architecture

- **SPA, no SSR.** Routing is TanStack Router, file-based: the file tree under `src/routes/` is the route graph. `src/routeTree.gen.ts` is generated by the router plugin in `vite.config.ts` on `dev`/`build` and is committed; `tsc` fails without it, so on a fresh clone run `npx vite build` once before `npm run typecheck`. Never hand-edit it.
- **Route groups:** `/` landing and `/login`, `/register`, `/forgot-password` are public, as are `/auth/verify-email` and `/auth/reset-password` (the BE emails links to them: its `APP_BASE_URL` must be this web client's origin); `/app/*` is the end user's personal-info area (see scope above); `/restaurant/*` is the restaurant owner portal; `/admin/*` is the admin area. `routes/app.tsx`, `routes/restaurant.tsx` and `routes/admin.tsx` are thin layouts over the shared `components/app-shell.tsx` (sidebar on `md+`, bottom tab bar below), which takes `title` and a `nav` array. Access is guarded in `beforeLoad`: `/app` and `/restaurant` need a signed-in user, `/admin` needs `role === 'admin'`, and `/login`, `/register` bounce signed-in users to `/app` (`features/auth/guards.ts`). Signed-out users go to `/login?redirect=<path>`; the target is validated by `safeTarget` so it cannot point off-site. The session lives in the Zustand store `lib/session-store.ts` (see API below). `role` (`user` | `admin`) comes from the BE on every session user and is enforced server-side (403 for non-admins); the FE only uses it to pick which UI to show (admins get a "Quản trị" item in the `/app` nav). There is no "restaurant" role: any user can create one restaurant and owns it, and `/restaurant` infers ownership from `GET /restaurants/mine` (404 means none yet, so the page shows the create form).
- **Layering:** `routes/` only compose `features/<name>/` (page-level components, hooks, stores); features never import each other (shared pieces live in `components/` and `lib/`). `src/api/` is the HTTP layer (see API below). Route files that export a component alongside `Route` trigger a lint warning, so keep components inline arrows or in `features/`. An inline arrow cannot call hooks (`rules-of-hooks`): put a component that needs hooks in `features/` (route params come from `getRouteApi('<path>').useParams()` there).
- **Admin:** `features/admin/`. Real (generated SDK): moderation queue and review page (`/admin/restaurants`, `/admin/restaurants/$restaurantId`, approve or reject restaurants and dishes; rejecting needs a reason and approved items can be taken down the same way) and the cash-flow/growth dashboard (`/admin/dashboard`, recharts, sends no `from`/`to` for the BE default of the last 30 Vietnam days). Still mock (`mock-*.ts`, replace when asked): the overview KPIs, users table (accent-insensitive search via `lib/text.ts`) and content tabs. Ad packages are deferred in the BE, so there is no screen for them.
- **Restaurants:** `features/restaurant/` is the owner portal (profile, menu with nutrition per serving, image upload). Dish and restaurant forms keep numbers as strings and map them with `toDishBody`/`toRestaurantBody`; users type "12,5" (comma accepted) and paste the Google Maps coordinate string "10.7769, 106.7009" (`lib/coordinates.ts`; the BE never parses links). Editing a dish sends it back to `pending`, so `DishForm` reports its dirty fields and updates send only those (`toDishPatch`); `null` clears `description`, `imageUrl` and `fiberG`. `lib/nutrition.ts` flags kcal far from 4P+4C+9F for both owners and admins. Pieces shared by owner and admin (`StatusBadge`, `RestaurantSummary`, `DishNutrition`, `RejectionNote`, `ConfirmDialog`) live in `components/`. Business rules live in `FoodFenBE/docs/marketplace.md`.
- **State:** server state via TanStack Query (`QueryClientProvider` is in `src/main.tsx`), local/UI state via Zustand, forms via react-hook-form + `@hookform/resolvers/zod` with zod 4 (types come from `z.infer`).
- **Alias:** `@/` maps to `src/` (set in `vite.config.ts`, `tsconfig.app.json` and the root `tsconfig.json`; shadcn reads the root one). Do not add `baseUrl`: TypeScript 6 deprecates it.

## Backend contract (for wiring features)

Wire format is camelCase. Error bodies are `{ message?, error?, errors?: { field: message } }`, not FastAPI's `detail`; `parseApiError` (`api/errors.ts`) turns any failure into `{ status, message, fields }` with Vietnamese fallbacks. `expiresAt` is epoch **milliseconds**. The BE allows all origins by default (`cors_allow_origins="*"`), and auth is bearer-token only (no cookies).

## API layer

- `src/api/generated/` is produced by `npm run api:gen` (`@hey-api/openapi-ts`: axios client, typed SDK, TanStack Query options) and **is committed**; never edit it. Regenerate when the BE changes: with the BE running use the default URL, otherwise export the spec from the BE code (`FoodFenBE/.venv/Scripts/python -c "import json; from src.main import app; print(json.dumps(app.openapi()))" > spec.json`) and run `OPENAPI_URL=spec.json npm run api:gen`. Call endpoints through the generated SDK/query options, not hand-written axios calls.
- `src/api/client.ts` (`configureApi()`, called once in `main.tsx`) sets `VITE_API_URL` (default `http://localhost:8000`) and an `auth` callback that supplies the bearer token for operations the spec marks as secured; a 401 on such a request triggers one refresh and one retry.
- Refresh (`src/api/refresh.ts`): the access token (memory only) is renewed shortly before `expiresAt`; refreshes are single-flight per tab and serialised across tabs with the Web Locks API, because the BE rotates the refresh token on every use. Only an explicit 401 from `/auth/refresh` ends the session; being offline never logs anyone out. The refresh call uses its own client without interceptors.
- Token storage: the user and **refresh token are persisted in `localStorage`** (`foodfen-session`) so sessions survive reloads and are shared across tabs; the trade-off is that XSS could read it. Moving the refresh token to an httpOnly cookie needs a BE change.
- `features/auth/session-sync.tsx` pings `GET /auth/me` while signed in (revalidates the session, keeps the profile current). `main.tsx` re-runs route guards when the session ends, so protected pages redirect to `/login`.
- Auth forms use `useSignIn`/`useSignUp`/`usePasswordReset`/`useSignOut` (`features/auth/use-auth.ts`) and `applyApiError` (`api/form-errors.ts`, shared by every form) to show server field errors; sign-out clears local state whatever the network does. `SubmitButton` and `FormError` live in `components/form-parts.tsx`.
- Uploads go through the generated SDK too: `POST /restaurants/mine/images` is multipart (field `image`; JPEG/PNG/WebP, max 5 MB, else 400 `{message}`) and returns an absolute `url`. Every `/auth/*` route shares one per-IP rate limit in the BE, so scripted local runs can hit 429.

## Styling and design

- All theme tokens live in `src/index.css` as oklch CSS variables with a light set and a `.dark` set. Dark mode is the `dark` class on `<html>`, driven by `lib/theme.ts` and the `ThemeToggle` component: it follows the OS until the user toggles, then stores the choice in `localStorage` (`foodfen-theme`); the inline script in `index.html` applies it before first paint. Text over photos must use the fixed `scrim` token with `text-white`, never `primary`/`primary-foreground`, because those swap between themes. The palette is an emerald green base. `--cta` (orange) is a custom token reserved for Premium and macro highlights; use it as `bg-cta text-cta-foreground`, nowhere else.
- shadcn is the `base-nova` style on Base UI (not Radix), and `cn` comes from the `cn` package. Its buttons are compact (`h-8`/`h-9`); public pages override with `h-11` to meet 44px touch targets. Surfaces use `rounded-2xl`, controls use the default radius.
- Font is Inter Variable, chosen because it has a Vietnamese subset and tabular figures for calorie numbers.
- **Icons: `lucide-react` only. Never use emoji anywhere** (UI, copy, code, comments, commit messages). Use a Lucide icon instead, and give decorative ones `aria-hidden`.
- The landing page (`features/landing/`) uses `motion` (`motion/react`) for scroll parallax and reveals; motion must respect `useReducedMotion`. Its photos are hotlinked from Unsplash and randomuser.me, and its testimonials and `stats.tsx` figures are mock data (marked in the files): replace them with real content and self-hosted assets before launch.
- House style from the design skills: no em-dashes in copy, no tracked-caps eyebrow labels, no decorative status dots, one CTA label per intent ("Dùng thử miễn phí" for sign-up).

## Gotchas

- TypeScript is pinned to 6.x (the Vite template's); 7.0 exists but is not adopted.
- `shadcn init` installed zod 3; the project is on zod 4. Check `package.json` after running shadcn commands.
- `shadcn add` asks to overwrite `button.tsx` when a component depends on it (the project's copy is customised). Answer no: `"n" | npx shadcn@latest add <name>`.
- npm blocks the `msw` postinstall. Node-side tests do not need it; for browser mocking run `npm approve-scripts` then `npx msw init public`.
