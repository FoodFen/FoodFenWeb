# Feature notes

Per-feature contracts and rules, moved out of `CLAUDE.md` so they are read only when a change touches that feature. Update the matching section in the same change as any rule it states.

## Routing & access

- **Route groups:** `/` landing and `/login`, `/register`, `/forgot-password` are public, as are `/auth/verify-email` and `/auth/reset-password` (the BE emails links to them: its `APP_BASE_URL` must be this web client's origin); `/app/*` is the end user's personal-info area (see scope above); `/restaurant/*` is the restaurant owner portal; `/admin/*` is the admin area. Signed-in areas live under the pathless layout `routes/_authed.tsx` (guard `requireUser`, renders the single `components/app-shell.tsx`, so the shell never remounts between areas; route ids carry the `/_authed` prefix, e.g. `getRouteApi('/_authed/admin/restaurants/$restaurantId')`). The shell is one nested shadcn sidebar driven by the static tree in `components/app-nav.ts` ("Tài khoản", group "Quán của tôi", admin-only group "Quản trị"; a group is a Collapsible, open by default when it holds the current route); below `md` the sidebar is a sheet opened from a sticky top bar and closes on navigation. `routes/_authed/admin.tsx` only adds the `requireAdmin` guard. Access: `/app` and `/restaurant` need a signed-in user, `/admin` needs `role === 'admin'`, and `/login`, `/register` bounce signed-in users to `/app` (`features/auth/guards.ts`). Signed-out users go to `/login?redirect=<path>`; the target is validated by `safeTarget` so it cannot point off-site. The session lives in the Zustand store `lib/session-store.ts` (see API below). `role` (`user` | `admin`) comes from the BE on every session user and is enforced server-side (403 for non-admins); the FE only uses it to pick which UI to show (admins see the "Quản trị" group in the sidebar). There is no "restaurant" role: any non-admin user can create one restaurant and owns it, and `/restaurant` infers ownership from `GET /restaurants/mine` (404 means none yet, so the page shows the create form). Admins do not own restaurants: the sidebar hides "Quán của tôi" (`userOnly` nav section) and `requireOwner` redirects them from `/restaurant/*` to `/admin`.

## Auth & session

- Refresh (`src/api/refresh.ts`): the access token (memory only) is renewed shortly before `expiresAt`; refreshes are single-flight per tab and serialised across tabs with the Web Locks API, because the BE rotates the refresh token on every use. Only an explicit 401 from `/auth/refresh` ends the session; being offline never logs anyone out. The refresh call uses its own client without interceptors.
- Token storage: the user and **refresh token are persisted in `localStorage`** (`foodfen-session`) so sessions survive reloads and are shared across tabs; the trade-off is that XSS could read it. Moving the refresh token to an httpOnly cookie needs a BE change.
- `features/auth/session-sync.tsx` pings `GET /auth/me` while signed in (revalidates the session, keeps the profile current). `main.tsx` re-runs route guards when the session ends, so protected pages redirect to `/login`.
- Auth forms use `useSignIn`/`useSignUp`/`usePasswordReset`/`useSignOut` (`features/auth/use-auth.ts`) and `applyApiError` (`api/form-errors.ts`, shared by every form) to show server field errors; sign-out clears local state whatever the network does. `SubmitButton` and `FormError` live in `components/form-parts.tsx`.

## Admin

- **Admin:** `features/admin/`. Real (generated SDK): restaurant management (`/admin/restaurants`, tabs Tất cả / Chờ duyệt / Đã duyệt / Bị từ chối kept in the `?tab=` search param) and review page (`/admin/restaurants/$restaurantId`, approve or reject restaurants and dishes; rejecting needs a reason and approved items can be taken down the same way) and the cash-flow/growth dashboard (`/admin/dashboard`, recharts, sends no `from`/`to` for the BE default of the last 30 Vietnam days). Also real and read-only: the overview (`/admin`, reuses `/admin/dashboard`), users (`/admin/users`, server-side search with cursor paging) and content (`/admin/content`, quizzes and quest definitions). The dashboard ends with a daily table (newest first, totals row). Restaurant search at `/admin/restaurants` is server-side (`GET /admin/restaurants`: `q` matches restaurant name, owner name or owner email, case-insensitive but accent-sensitive; URL params `tab` and `q`, cursor paging with Tải thêm, shows the BE `total`); the review page reads the owner from the detail response (`ownerName`, `ownerEmail`). Transactions: `/admin/payments` (`GET /admin/payments`, filters `q`, `status`, `planType`, `provider`, `from`, `to` all in the URL, cursor paging with Tải thêm, shows the BE `total` only, never sums over a page). Ad packages are managed in `/admin/ad-packages` (table plus one create/edit dialog; packages are hidden with "Đang bán" unchecked, never deleted).
- **Mascots:** `/admin/mascots` (`features/admin/mascot*`, `use-mascots.ts`): CRUD with per-state artwork (9 states, `idle` is the fallback) uploaded through `POST /admin/images` (downscaled in the browser to 1024 px on the longest side, as WebP, before upload; the 5 MB limit applies after). Calls use the generated SDK (`use-mascots.ts`); `mascot-states.ts` holds the state order and the ids the app draws itself. `bodyColor` is the circle behind the art (`#RRGGBB`; `null` = the theme green, light `#15803D` / dark `#4ADE80`), sent in a PATCH only when dirty. Contract: `FoodFenBE/docs/superpowers/specs/2026-10-30-mascot-admin-coin-reason-design.md`.

## Restaurants (owner portal)

- **Restaurants:** `features/restaurant/` is the owner portal (profile, menu with nutrition per serving, image upload). Onboarding: `/app` shows `MyRestaurantCard` (hidden for admins; name and status, or a pitch linking to `/restaurant`); with no restaurant, `/restaurant` shows the intro (benefits, steps, terms copy that is a draft pending legal review, and a required checkbox), and only the "Bắt đầu đăng ký" button leads to the create form at `/restaurant/register?accepted=true` (without `accepted` it redirects back; a user who already has a restaurant is sent to `/restaurant`). Restaurant form fields: phone is validated with `libphonenumber-js/min` (default country VN; `lib/phone.ts`), stored nationally without spaces for Vietnamese numbers ("0901234567") and as E.164 for foreign ones, and shown grouped ("0901 234 567") as a `tel:` link. Opening hours are 1 to 3 shifts applied to every day (`OpeningHoursField`, native time inputs, a shift may cross midnight, no overlaps), stored as "07:00-10:30, 16:00-21:00" (`lib/opening-hours.ts`); saved text `parseHours` cannot read is shown read-only (`legacyHours`) and omitted from the PATCH (`toRestaurantPatch`) unless the owner picks shifts. Location is a Google Maps picker (`LocationField` lazy-loads `LocationPicker`: Places (New) search restricted to Vietnam, click or drag the pin, "Vị trí hiện tại"); it needs `VITE_GOOGLE_MAPS_API_KEY` (Maps JavaScript API and Places API (New) enabled) and optionally `VITE_GOOGLE_MAPS_MAP_ID`, and without a key, or if Maps fails to load, only the coordinates text field shows (the form value stays the `location` string). Dish and restaurant forms keep numbers as strings and map them with `toDishBody`/`toRestaurantBody`; users type "12,5" (comma accepted) and paste the Google Maps coordinate string "10.7769, 106.7009" (`lib/coordinates.ts`; the BE never parses links). Editing a dish sends it back to `pending`, so `DishForm` reports its dirty fields and updates send only those (`toDishPatch`); `null` clears `description`, `imageUrl` and `fiberG`. `lib/nutrition.ts` flags kcal far from 4P+4C+9F for both owners and admins. Pieces shared by owner and admin (`StatusBadge`, `RestaurantSummary`, `DishNutrition`, `RejectionNote`, `ConfirmDialog`) live in `components/`. Business rules live in `FoodFenBE/docs/marketplace.md`. Paid placement is `features/restaurant-ads/` at `/restaurant/ads` (path fixed: PayOS/MoMo redirect back to it): checkout stores the order code in `sessionStorage` (`foodfen-ad-order`, `pending-order.ts`) and redirects to the provider; on return the page polls `GET /payments/{orderCode}` every 3 s while pending (the BE reconciles with the provider) and shows the outcome, clearing the key once it settles. Owner statistics live in `features/restaurant-stats/` at `/restaurant/stats` (own query hooks, status, dish counts, impressions, menu summary, ad payment history); "spent on ads" sums only the payment pages loaded so far and its label says so while more pages exist.
- Uploads go through the generated SDK too: `POST /restaurants/mine/images` is multipart (field `image`; JPEG/PNG/WebP, max 5 MB, else 400 `{message}`) and returns an absolute `url`. Every `/auth/*` route shares one per-IP rate limit in the BE, so scripted local runs can hit 429.

## Landing

- The landing page (`features/landing/`) uses `motion` (`motion/react`) for scroll parallax and reveals; motion must respect `useReducedMotion`. Its photos are hotlinked from Unsplash and randomuser.me, and its testimonials and `stats.tsx` figures are mock data (marked in the files): replace them with real content and self-hosted assets before launch.
